# M1 과제: 서버 단위 패스스루 프록시

> 담당: **구현은 본인**, 테스트와 리뷰는 Claude
> 완료 기준: `.venv/bin/pytest tests/m1 -v` 10개 통과 + 아래 "수동 확인" + 회고 노트 작성

## 1. 목표

클라이언트의 MCP 요청을 이름으로 지정한 upstream에 그대로 전달하는 프록시를 만든다.

```text
POST /proxy/{upstream}/mcp  ──►  upstreams[upstream]  (예: http://127.0.0.1:9001/mcp)
```

이 단계의 게이트웨이는 **도구가 무엇인지 모른다.** 그 한계를 직접 느끼는 것도 목표에 포함된다.

## 2. 시작 전에 읽을 것

- [ ] 스펙 2026-07-28 **Streamable HTTP** 절: 클라이언트가 보내는 헤더, 서버 응답의 두 형태(JSON, SSE), notification에 대한 202 응답
  https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http
- [ ] `scripts/probe.sh` 출력을 다시 보고, **요청 헤더마다** 누가 왜 쓰는지 정리해 보기

## 3. 구현 전에 답해 볼 설계 질문

답을 코드보다 먼저 `notes/m1-proxy.md`에 적는다. 정답이 하나인 질문은 아니다.

1. 클라이언트 요청 헤더 중 upstream에 **전달할 것**과 **전달하면 안 되는 것**은 무엇인가? 허용 목록(allowlist)과 차단 목록(denylist) 중 무엇이 안전한가?
2. upstream 응답을 다 받은 뒤 돌려주는 방식(버퍼링)과 받는 대로 흘려보내는 방식(스트리밍)은 각각 언제 문제가 되는가? SSE 응답에는 어느 쪽이어야 하는가?
3. upstream에 연결할 수 없을 때(서버 다운, 타임아웃) 게이트웨이는 무엇을 돌려줘야 하는가? HTTP 상태 코드와 JSON-RPC 본문 모두 생각해 보기
4. 본문을 파싱하지 않고 헤더만 보는 방식의 장점은 무엇인가? 헤더를 **믿어도 되는** 범위는 어디까지인가? (M5에서 다시 다룸)

## 4. 계약 (테스트가 기대하는 것)

```python
# gateway/main.py
def create_app(upstreams: dict[str, str], http: httpx.AsyncClient) -> ASGI 앱:
    """upstreams: 이름 -> upstream MCP 엔드포인트 URL.
    http: upstream 호출에 쓸 클라이언트 (테스트는 in-process upstream이 붙은 클라이언트를 주입함)."""
```

- 경로: `POST /proxy/{upstream}/mcp`
- 등록되지 않은 upstream: HTTP 404
- upstream의 HTTP 상태 코드, 본문, `content-type`을 그대로 돌려줌 (SSE 포함)
- 접근 로그: logger 이름 `gateway.access`, 요청마다 INFO 레코드 1개, 메시지에 upstream 이름과 `Mcp-Method`, `Mcp-Name` 포함
- **제약**: 요청 본문을 JSON으로 파싱하지 않는다

자유롭게 정해도 되는 것: FastAPI 또는 Starlette, 파일 구조, 로그 형식의 세부 사항, 404 응답 본문 형식.

수동 실행용으로 모듈 수준 `app`도 만든다 (예: `app = create_app(DEFAULT_UPSTREAMS, httpx.AsyncClient())`). 클라이언트를 언제 닫을지도 생각해 볼 것 (lifespan).

## 5. 진행 방법

```bash
.venv/bin/pytest tests/m1 -v          # 처음엔 전부 skip. gateway/main.py를 만들면 실패로 바뀜
```

테스트를 하나씩 통과시킨다. 추천 순서: 1(기본 전달) → 2(헤더와 상태 코드) → 4(로그) → 3(SSE).

### 수동 확인 (테스트로 확인할 수 없는 부분)

테스트 환경(httpx `ASGITransport`)은 응답을 버퍼링하기 때문에, **진짜 스트리밍이 되는지는 테스트로 확인할 수 없다.** 실제 서버로 확인한다.

```bash
scripts/upstreams.sh start
.venv/bin/uvicorn gateway.main:app --port 8000
scripts/probe.sh http://localhost:8000/proxy/math/mcp     # 직접 호출했을 때와 출력이 같아야 함
```

`slow` 서버에 `delay: 1`로 `count(n=5)`를 호출하고, curl `-N`으로 진행 알림이 **1초 간격으로** 도착하는지 본다. 5초 뒤에 한꺼번에 도착하면 어딘가에서 버퍼링하고 있는 것이다.
